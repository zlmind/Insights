原型 v3 · 平台登录状态（写作页连接条内新增一行）

对齐竞品词汇：wechatsync 的「平台登录状态」、蚁小二的「账号授权」。每平台一个状态； 通道/执行器等实现细节只出现在悬停解释里（悬停任意 chip 试试）。

场景 A · 正常在线
账号登录 3 个平台可推送 · 刚刚检测
  • 公众号
  • 小红书
  • 知乎
  • 头条号 去登录 ↗
  • 抖音 去登录 ↗
已登录，可推送 未登录（点击去登录） 暂不支持检测 检测服务离线
场景 B · 检测服务离线（昨天：扩展被重装后没重新配对）
账号登录 检测离线 · 无法确认登录状态
  • 公众号 去恢复 ↗
  • 小红书 去恢复 ↗
  • 知乎 去恢复 ↗
没有执行器在线时，不假装知道登录状态 —— 整条转灰、条头说明原因、给恢复入口。 这正是昨天按钮灰掉时用户最缺的信息。
场景 C · 部分平台暂无检测能力（探测未实现时的诚实降级）
账号登录 1 个平台可推送 · 刚刚检测
  • 公众号
  • 头条号
  • 抖音
「暂不支持检测 ≠ 未登录」。v1 方案里扩展对没探测的平台硬报「未登录」是错的，这里改为显式灰态。 spec 阶段决定是否给知乎/头条/抖音/小红书补真实探测。

行为注记（写 spec 时固定）： ① 状态接口 GET /agent/login-states.json：每平台 {state: ok|logged_out|unknown|offline, at, login_url}，由在线执行器的心跳汇总而来； ② 词汇表对齐竞品：平台 / 登录 / 已登录 / 未登录 / 去登录 / 检测；「agent」「扩展」「通道」不进客户文案； ③ 未登录 → 点击直达该平台登录页，登录后 ≤30s 自动转绿（心跳周期决定）； ④ 检测离线 → 条头说原因，chip 给恢复入口（发布队列页的配对）； ⑤ 悬停细节保留执行器来源（浏览器扩展 / 推送程序，X 秒前）——排障信息收进 tooltip，不占版面。
